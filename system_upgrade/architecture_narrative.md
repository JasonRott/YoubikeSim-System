# 系統架構脈絡檔（設計決策的故事）

本檔以「說故事」的方式，記錄我們如何一步步決定這個 YouBike 模擬系統的每個設計細節，
以及背後的理由與取捨。目的是讓最終統整報告能直接引用設計脈絡，而不只是看程式。

與 `planned_upgrades.md`（待辦清單）、各 `phaseN_*.md`（實作紀錄）、`references.md`（參考資料）互補：
- 本檔講「為什麼這樣設計」。
- phase 報告講「這次具體做了什麼、怎麼驗證」。
- planned_upgrades 講「還想做什麼」。
- references 講「參考了哪些研究、各參考了什麼」。

**慣例**：之後每一次像這樣的設計討論（決策、理由、取捨、查證結果），都要記到本檔；
有引用到的研究/資料則補進 `references.md`。

## 1. 為什麼用離散事件模擬（DES / SimPy）

YouBike 的核心是「離散事件」：使用者在某時刻到站、租車、移動、還車。
這些事件改變站點的車輛/空位狀態，而我們關心的服務品質（借得到車、還得到位）
正是這些狀態隨時間的演化。SimPy 的 process / resource 模型天然契合：
- `Station` 用 `simpy.Container` 管理車輛與空位。
- `Rider` 是一個 process：租車 → 三段式移動 → 還車（必要時再尋站）。
- 需求用 NSPP（非齊次卜瓦松過程）產生器，依每小時 λ 抽 inter-arrival。

## 2. 為什麼要 Dummy Node（行政區近似）

若直接建「站對站」OD 矩陣，1700+ 站會產生約 300 萬個 OD pair，
資料稀疏又難以維護。我們改用行政區作為中繼（Dummy Node），把一次移動拆成：

```
起點站 → 起點行政區 → 目的行政區 → 目的站
```

這讓巨大的 station-to-station OD 拆成較小的「站點選擇同區/出區」、「行政區之間」、
「進入目的區後選站」三層分布，資料量與穩定度都可控。後來的
`StationExitRoutePlanner` 就是把這個 station-first 的分層抽樣接回 Rider 流程。

## 3. 為什麼「借不到車就流失」是刻意設定（重要）

直覺上，使用者到空站借不到車，會走去隔壁站借。但我們**刻意讓他直接流失**，理由是：
**我們的需求 λ 是用真實資料（站點車輛數變化）推估的**。如果現實中有人在 A 站借不到、
走去 B 站借成功，那筆借車已經被記在 **B 站的 λ** 裡了。若模擬再讓他從 A 走到 B，
等於把同一筆需求算兩次。所以「A 站流失」其實正確反映了「A 站的真實 λ 只計成功的借車」。

對照：**還車遇滿站時仍會改去鄰近站**（return 端不流失），因為還車一定要完成，
且真實資料中還車也記在實際完成的站點。兩端的非對稱是有意的、與資料來源一致。

（程式：`Station.rent_bike` 失敗記 `shortage` 即離開；`return_bike` 滿站會 reroute。）

  後來改用分開的 `stations_arrival_rates_weekday.csv` / `_weekend.csv`（兩者 λ 不同）。
- **OD transition**：`週間/週末起訖站點統計_202512.geojson`（2025/12 起訖統計）。

- **initial bikes / benchmark**：`kpis_1.csv` 的 `avg_fill_ratio`、`bike_avail_rate`、`dock_avail_rate`。

清理決策：
- `臺大專區`（OD 來源命名）對應到 static 的 `臺大公館校區`，建立 alias 合併。
- 4 個只在 rate 檔、不在 static 的站（500105088/108127/108186/110108）排除。
- `500109131` 只在 kpis、其餘檔都沒有，視為退役站不納入。

## 5. arrival rate：2 小時 → hourly NSPP，以及 weekday/weekend 切換

2 小時區間的 λ 直接複製到對應的兩個小時（例如 08:00-10:00 → hour 8、hour 9）。
loader 會把 hour key 轉成 int，模擬以 `hour_of_day = (分鐘//60) % 24` 取當下 λ，
因此 24 小時模擬會正確逐時循環。`--profile` 同時決定 OD 矩陣與 arrival rate 目錄。

## 6. 真實 capacity 與 initial bikes

- capacity 直接取 dynamic 的 `Quantity`（7~99，平均 28.3）。
- initial bikes = `round(capacity × avg_fill_ratio)`（全系統平均 10.4 台），
  比早期假設的固定 15 台更貼近真實，且讓初始狀態就反映各站的真實鬆緊。

## 7. travel time：從固定值走向 probabilistic（規劃中）

初版用「直線距離 ÷ 固定 12 km/h」近似旅行時間，明確是占位用。
決定改成更有 probabilistic programming 味道的兩層抽樣：

1. **道路距離 ≈ 直線距離 × 繞路係數（circuity / detour factor）**，
   且繞路係數本身用高斯分布抽樣（不是每個人都走出完美最短路）。
   文獻參考（見第 11 節）：都市 Euclidean→道路距離一般約 1.2 倍；
   歐洲都市平均徑向繞路約 1.34；各國 circuity 介於 1.12–2.10；
   自行車/步行通常比開車高。**目前未找到台北市專門研究**，
   先暫採平均繞路係數約 1.3（可調），標註為待校準參數。
2. **車速也用高斯分布抽樣**（考慮紅綠燈、路口延誤造成的實際速度低於自由速度）。
   都市騎乘實際平均速度常落在約 12–15 km/h（含停等）。

這樣旅行時間 = 道路距離 / 抽樣車速，且兩個來源都有隨機性，較貼近真實異質性。

**已實作（2026-06）**：`scenarios/real_system_scenario.py` 的 `sample_trip_minutes`
以 `circuity ~ N(1.3, 0.15)`、`speed ~ N(14, 3)` km/hr 抽樣，每趟行程抽一次。
參數可由 CLI 調整，並記入 `summary.json` 的 `travel_time` 區塊。

**截斷方式（2026-06 調整）**：原本 circuity 用 `max(1.0, ...)` 夾住，會在 1.0（純直線）
堆出不自然尖峰。改為 `truncated_gauss`：在 ±3 SD 內用**重抽（rejection）**取樣，
不夾住故無尖峰。但因**道路距離幾何上不可能短於直線**，仍保留 1.0 為物理硬下限
（重抽而非夾住，所以靠近 1.0 的值會平滑變稀，不會堆積）。速度同樣以 ±3 SD 重抽、
物理下限 3 km/hr。`TRUNC_N_SD = 3.0`。

**「旅行時間偏短」診斷（2026-06）**：使用者反映模擬時間比體感短。查證 + 資料分析結論：
- 官方分析以 **~10 km/hr** 當參考速度；我們的**有效直線速度 = 14 / 1.3 ≈ 10.8 km/hr**，與官方一致。
- 官方 YouBike **最常見租借時長為 5–7 分鐘**（眾數）；我們模擬平均約 5.5 分、中位數約 3.7 分，
  與官方眾數同量級——**多數 YouBike 行程本來就很短**（最後一哩、捷運接駁）。
- 殘差落差主因是**OD 距離偏短**：模擬中位直線距離約 0.64 km，略短於官方「5 分鐘≈1 km」的典型；
  80% 行程為同區短程（距離衰減為 bike-share 真實特性，但可能略過度集中於鄰近站）。
- 也要注意官方「平均租借 27.1 分」是**持有時間**（受前 30 分鐘免費行為拉高），不是純騎乘時間，
  不可與我們的純騎乘時間直接比較；加上我們未計入走到站、找車/找位等 overhead。
- 結論：純騎乘時間其實與官方資料相符，不建議為了「變長」而把速度降到官方 10 以下；
  若要再貼近，較合理的方向是檢視 OD 目的地是否過度集中鄰近站。
- 工具：`scripts/plot_travel_time_distribution.py` 可對任一報告輸出時間/距離分布圖與摘要。

## 8. OD 資料缺口：175 個站「有 λ 但無 OD origin row」（重要資料問題）

查證結果（weekday）：
- arrival-rate 站點 1739；OD `station_exit_transition` 中**有 origin row 的站只有 1564**。
- 因此 **175 個站有租借 λ（有人在此借車），但 OD 來源裡沒有任何「從這站出發」的紀錄**，
  我們不知道這些站的使用者會去哪 → 目前 fallback 成「同區均勻選站」。
- 約占行程的 5%（每次 2hr smoke 約 190–216 筆 fallback）。

成因：**λ 與 OD 來自不同資料集**。λ 來自站點車輛數變化推估，OD 來自 2025/12 起訖統計
（可能只收錄達一定門檻的站對、或涵蓋不同期間），所以低流量起點站在 OD 裡沒有 row。
這不是「站不存在」，而是「這站的目的地分布在 OD 來源中缺席」。

補充查證（2026-06）：YouBike 台北**沒有公開逐筆 trip 紀錄**；公開的是「起訖站點統計」
（站對站交易次數彙整，即我們的 OD GeoJSON）與即時站點資料。值得注意的是，OD 起訖統計是
**實際交易次數**（使用者借→還），理論上比「車輛數變化推估的 λ」更不受調度污染
（卡車補/抽車不是一筆交易）；但 OD 只有彙整、無逐時，故無法直接取代需要逐時的 λ。
這點對第 10 節校準討論有幫助：OD 交易量是相對乾淨的需求訊號，可作為校準的旁證。

影響與後續：fallback（原為同區均勻）只是讓模擬不中斷，這 175 站的目的地分布並不真實。

### 車輛佔用時間校準（2026-06，重要修正）
使用者指出：我們關心的是「車被借走、不在站＝不可用」的時間，**而真實「平均租借時長」正反映這個**。
我先前說「平均租借時間不能比」是錯的。模擬原本只算純騎乘（~5.5 分），等於車一下就還回站、補太快。
- 修法：**車輛佔用時間 = max(純騎乘, 租借時長抽樣)**，租借時長 ~ 對數常態(μ=2.8, σ=1.0)
  校準到真實（眾數~6 分、平均~27 分），上限 180 分（使用者指定，原 240 太多）。
- 滿站改去鄰站只算**額外騎乘**（`station_to_station` 用純騎乘），不再疊加一次持有，避免重複計算占用。
- 驗證：2hr smoke 佔用平均 27.4 分（真實 27.1）、眾數~6、右偏，與真實租借分布吻合。
- 速度不調（有效速度 14/1.3≈10.8 已對上官方 10）。

### 同站來回（round trip）reintroduce（2026-06，規劃中）
Phase 2 刻意抽出的「起點=終點」同站交易，決定加回模擬（是真實使用者的一部分）。資料與研究：
- 同站占比：**週間 10.9%、週末 22.5%**（我們資料）；文獻同站來回約 11%（吻合），且**多為休閒/購物**
  （週末更高完全合理）。
- 研究：**同站來回租借更長（40.35 分）vs 單程（22.47 分）**——修正「同站=短」的直覺，genuine 同站其實更長。
- 業界把 **< 60 秒**視為 false start（誤借/壞車重新插回）並過濾掉；壞車遭遇率不低（某研究~17% 車不可用）。
- 使用者洞見：同站應是**兩族群混合**——真正要用（休閒，較長）+ 借錯/壞車（立刻歸還，<60 秒）。

**最終決議與實作（2026-06）**：
- **移除 false start**：因 OD 轉移矩陣已過濾 <60 秒、λ（車輛數變化）也抓不到 <60 秒拿了又插回，
  且其對站點可用性影響可忽略——硬加等於塞入校準資料中沒有的東西。故**同站交易全當「真正休閒來回」**，不分 false start。
- **佔用時間分流校準**（用台北實測整體 27.1 分 + 文獻同站約 1.8× 單程）：
  - 單程：對數常態(μ=2.74, σ=0.975)，mean≈25 分、mode≈6 分，且 `max(純騎乘, 抽樣)`。
  - 同站來回：對數常態(μ=3.48, σ=0.81)，mean≈45 分、mode≈17 分，不套騎乘下限（距離≈0）。
  - 加權回去：週間（10.9% 同站）整體≈27 分（對上台北）；週末（22.5%）整體≈29.5 分（更長，符合休閒）。
- **route planner**：每筆租借以 `self_station_ratio`（由 OD build metadata 讀，週間 0.109/週末 0.225）抽中同站來回（目的站=起點站）。
- **驗證**（weekday 2hr）：同站 10.6%、同站佔用 44.1 分、單程 25.0 分、整體 27.0 分——全部命中目標。
- **視覺化**：站點層級時，同站來回 rider 改為**較小的點繞著原站 node 旋轉**（角度隨進度推進約 2 圈），直到歸還時間，避免誤判為靜止或進站。

## 9. 視覺化設計脈絡（Phase 7 / 8）

地圖式視覺化是為了「直覺觀察全市站點狀態隨時間變化」。關鍵決策：
- **edge 改直線**：曲線繞行太醜太複雜，改一般 graph 直線；node 圖層在上、rider 過 node 淡化
  （不完全消失，避免誤判為進站）。
- **顏色隨時間變化**：早期只用最終 snapshot 著色 → 看起來凍結。改由 events 重建每站
  時序佔用率，逐幀著色（站點層級變化明顯，行政區層級因平均而平緩）。
- **畫面比例**：根因是直長畫布在寬螢幕以高度 fit、左右大量留白。改成 viewBox 跟隨視窗像素，
  node 採「部分反向縮放」（指數 0.5：放大可讀又拉開解擠）。
- **站點層級畫全部站點 + 移除「區外」中繼**：因為全站都畫了，跨區 rider 可直接連真實目的站；
  重設仍聚焦選定行政區、其餘可平移。
- **疊真實行政區邊界**：來源是 TWD97 TM2（公尺），站點是 WGS84（度），必須先投影轉換
  （pyproj）再套用與站點相同的投影才會對齊；為此整套座標維持等比縮放。
- **行政區 node 放在邊界面積中心**（而非站點重心），視覺較平衡。
- **邊界共用邊不抽稀**：抽稀會讓相鄰區共用邊界取到不同點而出現複數平行線；保留原始頂點即重疊成單線。

## 10. 衡量指標與校準哲學（規劃中，核心）

### 10.1 系統服務品質指標：「站點優良時段占比」
定義：一天中（限 06:00–23:59），站內車輛數維持在容量 **20%–80%** 之間的時間比例。
- 衡量**整體系統**：所有站點此指標的平均。
- 偵測**極端站**：看所有站點此指標的**分布**——左側肥尾代表有一批站長期失衡；
  也可用某個低百分位（如 5th/10th percentile）當門檻指標。
此指標屬「服務水準 / 維持健康狀態時間比例」類，直觀且可比較不同政策。

**真實 benchmark 已就位（2026-06，組員提供）**：存於
`data/benchmark/percentage_of_excellent/`（每站每日 + 每日系統平均 + 分布圖）。
真實統計（22 天、1744 站）：mean 0.607、median 0.603、P5 0.246、P10 0.329、P90 0.910；
全天健康(=1.0) 4.2%、極端惡劣(≤0.25) 5.2%。這是 time-to-fail 校準的比對基準。
下一步：在模擬端實作同定義指標（06:00–23:59、20–80% band），與此 benchmark 比對系統日均、分布與低百分位。

**已實作 + 第一次 24 小時模擬（2026-06）**：
- `run_metrics` 加入 `_excellent_fraction`（每站在 06:00–24:00 內車輛落在 20–80% 容量的時間比例），
  輸出系統 mean/median/P5/P10/P90、全天健康占比、極端惡劣(≤25%)占比，並與真實 benchmark 並列。
- runner 以 `load_excellent_benchmark` 讀真實 CSV 算 benchmark 統計傳入對照。
- **首次 24h weekday（seed 20260602）結果（無調度）**：
  ```text
  優良時段占比  模擬 vs 真實
  系統平均      25.9%  vs  60.7%
  中位數        17.7%  vs  60.3%
  P10           1.3%   vs  32.9%
  極端惡劣(≤25%) 59.6%  vs   5.2%
  見車率        74.4%  vs  95.7%
  shortage 59,939、full 59,936（229,092 arrivals）
  ```
- 解讀：無調度的系統在一天內嚴重退化（近 6 成站點落入極端惡劣區），與真實（有 YouBike 內生調度）差距巨大。
  **這個差距正是調度的價值**，也是 time-to-fail 框架要量化的對象。方向完全正確。
- λ 日需求 228,983 與模擬一致；對台北超高使用量系統屬合理量級（OD 月統計彙整期間未定，列為可選交叉檢查）。
**時間解析 time-to-fail 已實作（2026-06）**：

### 無調度崩潰速度的合理性評估（2026-06，重要討論）
觀察：無調度下健康站比例約 07:00 跌破 benchmark，午後僅 ~20%（weekend ~12%）。評估：

## 14. 調度 benchmark 設計（2026-06，下一階段地基）

目標：定義一條「任何調度策略都必須超越」的基準線，避免只跟「無調度」這個太弱的對象比。

### 三個錨點
- **下限 floor**：無調度（健康 ~20%、07:00 fail）。政策至少要明顯優於此。
- **上限 ceiling / target**：真實系統（優良占比 ~60.7%、永不 fail）。理想目標。
- **Benchmark 調度器**：簡單但合理的策略，落在中間，是「要超越的那條線」。

### Benchmark 調度器 = 「貪婪門檻式再平衡」(greedy threshold rebalancer)
- 資源（= 成本）：T 台卡車、每台容量 Q、用現有 travel-time 模型移動；可設定運作時段。
- 規則：每台閒置卡車前往**目前偏離健康帶 [20%,80%] 最嚴重的站**——過滿載走、過空補車，拉回 ~50%，
  受卡車載量/空間限制，完成後前往下一個最危急站，持續運作。
- 成本指標：總卡車里程 / 時數、搬運車輛總數、車隊規模 T。

### 公平比較協定
- 同需求、同 seed、同初始，只換調度模組。
- 比兩面向：**服務**（優良時段占比 mean / P5 / P10 / time-to-fail）與**成本**（卡車里程/時數）。
- 政策「贏過 benchmark」= **Pareto 支配**（服務 ≥ 且成本 ≤，至少一項嚴格更好）。

### 校準選項（建議）
- 調整 benchmark 車隊規模 T，使其優良占比 ≈ 真實 60.7% → benchmark = 「用最笨方式達到真實服務水準」；
  好政策須**更省成本達同服務**或**同成本達更好服務**。
- 待補：查真實台北 YouBike 調度車隊規模以定 T；查不到先取可辯護數字並做敏感度分析。

### 實作待辦（下一階段）
- Dispatching Truck class（位置、載量、移動用 travel-time）。
- 補車/抽車事件（改變站點 bikes/docks，記入 event log）。
- greedy benchmark 政策模組（可插拔，類似 route_planner 的插拔方式）。
- 比較輸出：無調度 / benchmark / 政策 三者並列（服務指標 + 成本）。

### 16.2 結果分析核心 = SC Ratio（提案 p.13）
```
SC Ratio = ServiceLevel / DispatchingCost
ServiceLevel  = 1 − (Total Bike Shortages + Total Full-Station Events) / (Total Arrivals + Total Returns)
DispatchingCost = C_trip × 出車次數 + C_mileage × 總里程
```
注意：提案的 ServiceLevel 是「流失需求比率」，與我們的「優良時段占比(20–80%)」是**不同指標**。
**決策②：兩者並列同等呈現**——SC Ratio 與 優良占比/time-to-fail 都當頭條，互補。

### 16.3 組員調度規則摘要
- 站點分型：**易多站**（易客滿，抽車，target=LCL+10%=30%）、**易少站**（易缺車，補車，target=UCL−10%=70%）；LCL 20% / UCL 80%。預期性目標值（反向過量迎尖峰）設計佳。
- **Policy 1 固定巡迴**：每日 2 班、各 1.5hr（晨峰前、晚峰前），裝 15 台出發，依載量狀態過濾候選（滿車只補/空車只抽/半載皆可），到偏離最大站補/抽，1.5hr 內最後一單做完。
- **Policy 2 動態觸發**：閒置待命、每 5 分掃描；觸發＝有站 100%/0% 或 ≥3 站破 UCL/LCL；選站 `Score=(Current−Target)²/(Distance+0.5)`；全區健康即返場。
- 共同：卡車 15km/h（座標直線距離）、handling=3+0.5×台數 min、集散場 300 台、補/抽量受載量與空位限制、資源耗盡回場重置 15 台。

### 16.8 實作確認（2026-06，使用者拍板）已落地於 `src/youbike_sim/dispatch.py`
1. **集散場定位 = 站點幾何中位數（Weber point）**，非算術重心。理由：要最小化「到各站加總距離」，
   數學正解是幾何中位數（算術重心只最小化距離平方和）。以局部等距投影跑 Weiszfeld 迭代求解（`geometric_median()`）。
   （未來可加「以站點活動量加權」的加權幾何中位數，更貼近期望行駛距離；目前依使用者「所有站點」採不加權。）
2. **卡車車速 = 50 km/h，每段旅程高斯抽樣**（`N(50,10)`，截斷下限 10）。它是汽車，速度遠高於單車。
3. **Policy 1 選站 Score** = `|當前車數 − 目標車數| / (與卡車當前位置實際距離km + 0.1)`，取最大；**同分隨機**（非站號）。
   這同時解掉 §16.5 第 1 點的「(km)最大」模糊：原來就是這條 score。與 Policy 2 差異＝Policy 2 用平方放大極端、距離常數 0.5。
4. **SC Ratio 的 ServiceLevel = 缺車/滿車**（lost demand）：`1 − (缺+滿)/(借互動+還互動)`。
   理由：忠於提案 p.13、最直覺、與成本配對最有意義。**band 占比（20–80%）維持並列第二指標**（補 censored-demand 盲點、有真實 benchmark 60.7%）。
   - 站點現況分型（取代靜態 易多/易少，避開時段翻轉）：到站掃描時 低於 LCL→補至 70%、高於 UCL→抽至 30%；
     此即提案 p.12 Dynamic Threshold 字面邏輯。
   - 成本帳：trips（出車次數）、total_km（里程）、bikes_moved、wasted_visits；DispatchingCost = C_trip×trips + C_mileage×km。
   - 集散場＝有限緩衝庫存（預設每區 300），出車補滿至 15、返場清/補至 15；庫存可耗盡（破單車守恆，已計帳於 depot_inventory_end）。

### 10.2 校準難題：真實 λ 內生了 YouBike 的調度
因為 λ 是用站點車輛數變化推估的，**YouBike 的調度行為已經內生在 λ 裡**
（卡車補車會看起來像一批還車）。所以「無調度模擬」用這個 λ，與「有內生調度的真實」
本質上不可能完全對齊——這是資料層面無法直接拆解的限制。

### 10.3 我們的校準/評估構想：time-to-fail（divergence 起點）
1. 跑**完全無調度**的模擬，用 10.1 的指標持續比對模擬 vs 真實。
2. 觀察**從哪個時間點開始，模擬與真實出現顯著差異**（time-to-fail / time-to-divergence）。
   這個時間點當作 baseline 校準基準：它衡量「拿掉調度後，系統多久開始撐不住」。
3. 後續評估調度策略的**純效能**：至少要把 time-to-fail 推到涵蓋整個模擬時段（追上真實「永不 fail」），
   再比其他指標（服務品質分布、成本）。

### 10.4 與文獻的關係（見第 11 節）
- 「觀測到的 trip 是被 availability 審查（censored）後的需求下界」是**成熟且被廣泛接受**的觀點
  （censored demand 文獻）。我們點 3 的非對稱流失設定正與此一致。
- 「移除調度後系統會退化、且尖峰最先失效」也有模擬研究佐證。
- 我們的「time-to-divergence 當校準/評估基準」目前**未找到完全相同的已發表方法**，
  較接近「no-rebalancing degradation」類研究的精神；屬於合理的原創綜合，可在報告中說明。
- 一個更深的污染點：λ 由車輛數變化推估，會把調度卡車的補/抽車誤計為還/借，
  使 λ 本身被調度污染。若要更乾淨，可考慮改由**起訖 trip 紀錄**重新推估需求
  （OD GeoJSON 偏向實際使用者 trip），但這是較大的改動，列為選項。

## 18. 成本模型 + 閘門/休息 + 兩個混合 Policy（2026-06 討論定案）
文獻：調度目標 = 站點偏離懲罰 + 車輛營運(行駛+裝卸)；常見簡化「$100/次 + $1/km」其實把人力包進 per-trip；
「人力按時計薪通常是最大宗成本，故常以最小化總時間為目標」。台灣貨車司機 ~NT$53.5k/月 ≈ NT$300/hr。
來源：SBRP(Springer s13676-012-0017-6)、rebalancing MIP(Medium)、VRP objectives(elogii)、薪資公秤/Indeed。

### 18.1 成本模型（採用）
`DispatchingCost = C_labor·工時(hr) + C_km·里程(km) + C_trip·出車次數 (+ C_fix·T 選用)`
- 預設（NT$，可調，之後做敏感度）：**C_labor=300/hr、C_km=8/km、C_trip=50/次**；C_fix~700/車·日（同車隊相消，僅車數敏感度需要）。
- ⚠️ 不可同時用文獻的大額 per-trip 與獨立人力（會重複計）；故 C_trip 僅放發車雜支。
- **工時 = 值勤含待命（休息不計薪）**〔使用者選〕：
  - P1：人只在排定 2×1.5hr=**3hr/車·日** 值勤 → 人力便宜、其餘時段無人顧。
  - P2/3/4：值勤窗內待命也計薪 → 人力貴，誠實反映「全天保護」的代價。

### 18.2 閘門 + 人力休息（解 P2 無謂出車；人車綁定）
- **行動量門檻 `min_action_bikes=5`**：站點偏離目標 ≥5 台才算候選（不為差 1–2 台出動/繞路）。直接解決「出車卻做不了什麼」（因無跨區調度而起）。
- **值勤窗** 預設 06:00–24:00；窗外下班（不計薪/不出車）。
- **強制休息**：連續工作 ≥240min → 休息 45min（不計薪）；**出車冷卻** 每次返場後 10min。
- 這些同時讓 P2 變合理（少而精）且讓「工時」成本有意義。

### 18.3 反應觸發帶改 10/90（使用者洞見）
原 P2「≥3 站破 80/20」太鬆（大區幾乎全天成立→狂出車）；純危急 100/0 又太晚（到 0% 已 shortage）。
故反應層採**內警戒帶 `alert 10%/90%`**：≥3 站跌破 10% 或衝破 90% 即出動——比 80/20 緊、比 0/100 早。
（Policy 2 仍保留教科書原版 80/20+≥3+100/0 作為對照；10/90 用於新混合 P3。可另做 P2 變體。）

### 18.4 四/五種政策（全部保留於 POLICIES）
- none＝無調度；fixed＝P1 固定巡迴；dynamic＝P2 動態觸發（原版）。
- **P3 hybrid_anticipatory**（方案甲）：尖峰前排程預置巡迴 ＋ 其餘時間對 ≥3 站破 10/90 反應式出車（平方選站、含閘門/休息）。
- **P4 hybrid_smartshift**（方案乙）：排定班次（P1 timing）＋ 班內用 P2 平方選站 ＋ 全區健康即提早收工（省成本）。

仍在調參期，所有 performance 數字僅供參考，先不下「哪個 policy 絕對更好」的定論。SC Ratio 結論對成本係數敏感。

## 22. 重新框定：以「真實 true standard (0.607)」為評估基準（2026-06，關鍵）
使用者洞見：先前分析淪為「高品質＝高成本」的內部取捨；但真實世界的優良占比 0.607（真實 YouBike 連同其完整調度達到的水準）給了我們一條 **true standard**。
**任何調度策略都必須達到/超越 0.607，否則只是「用較低品質換效率」——劣於現實，不算成功。** 圖：`report/exp03_fleet_sweep/vs_true_standard.png`。

關鍵發現（震撼且重要）：
- **沒有任何測試設定達標**：全場最佳 P3 n=10（每區 10 車、~1.03M NT$/日）僅 **0.584**，仍差真實 **0.023**。

- 即整條服務-成本 Pareto 前緣**整條都在「劣於真實」區**。重新框定後，真正的目標是「**達服務 ≥ 0.607 的最小成本**」，目前無解。

## 31. 最佳化上界（optimal_ub，2026-06）
目的：給定車隊規模的**理論服務天花板**，區分「政策不夠好」vs「車隊/資源本就不夠」。
- 上界 ≈ 政策 → 政策已逼近極限；上界 ≫ 政策 → 政策有進步空間；上界 < 0.607 → 連理論最佳都輸真實（資源/結構問題）。
設計（`optimal_ub_controller`，每區一個控制器、非卡車）：
- 每 5 分鐘把各站推向 **50%**；**集散站退化成免費、瞬間、無限容量緩衝池**（surplus→池、池→deficit，守恆）。
- **忽略集散站物流/路徑/行駛時間** → 完美自由調度。唯一限制＝**車隊吞吐量**（每間隔 = T×(容量/搬運時間)×5min；T≤0→無限）。
- 合法上界：自由路由 ≥ 真實卡車、同車池、吞吐高估（忽略行駛）。任何政策皆 ≤ 它。搬移記為 truck_replenish/withdraw(mode=ub) 供 metrics 重建。
- **「忽略集散站」確切意思**＝不模擬集散站的物流限制（不需卡車搬、不管耗乾/容量），但仍守恆（集散站當免費緩衝池）。
版本：**UB-∞**（trucks=0，無限吞吐＝絕對天花板，測「總車數+5分粒度夠不夠到 0.607」）、**UB-T**（trucks=T，該車隊天花板，跟同車隊政策比）。
CLI：`--dispatch-policy optimal_ub --trucks-per-district {0=∞ | T}`。結果見 §31.1（待跑完填）。**數字 provisional（等 06:00 快照）**。

## 35. P7 配對協調政策（pair_coord，2026-06）
**動機**：exp07/08 證實破 0.607 是協調限制（吞吐夠、P3/P2/P6 飽和 ~0.58–0.60、離 UB 差 0.05–0.10）。現行政策各車各自貪婪（雖 `_claimed` 已去重同站），協調損失主要來自**集散場往返**與**未做就近 surplus→deficit 鏈式搬運**。P7 把區間 Policy 2「虛擬結算法／全域 flow 配對」**套到區內站點層**。

**機制**（待命族、全天值勤、每 scan 重解）：
- `DispatchSystem.plan_move(truck)` 全域回傳一筆任務：
  1. **pair**（優先）：surplus(>UCL,值得服務)→deficit(<LCL,值得服務) 配對，score = 可搬台數 /(車→盈餘 + 盈餘→赤字 距離 + const)，取最大（鏡像 Policy 2 貪婪最短距離 + 併入可搬量與車距）。

- `pair_coord_process`：取任務→鏈式「過滿站 serve_to_target(抽到 low) → 缺車站 serve_to_target(補到 high)」；`_claimed` 鎖住配對兩端去重；無事卸載回場待命；stall 防呆。

### 42.2 夜間母車成本模型（定案 2026-06，compact 後第一步）

## 43. 多日改「連續模擬」+ 守恆修正（重大重構，2026-06）
**起因（使用者抓到）**：先前多日是「每天獨立跑一支模擬、午夜拍快照接力」。交接時**快照只抓到「站點+集散場」的車，抓不到「在路上/在卡車上」的車（約3100台）** → 我舊的 `run_multiday`(Model A) 用守恆殘差 `集散場=26156−站點−維修` 把這些車**算回集散場**（總量守恆 26156，但物理上放錯——騎車的人是還到「站點」不是集散場）；我中途的 Model B 改「結轉昨天集散場剩量」更糟，**直接漏掉那3100台→每天少~2700台→PoE崩(0.592→0.325)**。

### 43.1 連續多日的設定決策（使用者定案）
- **OD 改全週間**（連續多日不切換週末 OD）。理由有二（使用者要求標註）：
  1. **模擬系統難改**：OD 機率烤進模型結構，午夜換 OD 侵入性高。
  2. **週末 OD 跑出的 PoE 偏離真實數據**（§41 週末薄資料 artifact：15%資料致假性方向失衡），原始週末 OD 本就難用、不可靠。

- **區間調度只做「虛擬結算法」一種**（不複雜化）；多日跑 **none vs virtual** 兩條（none=基準線、非方法）。
- **P7 調參打「穩態」不是第一天**（使用者「長時間調參」直覺正確）：連續模擬先得「穩態快照(如第7天態)」，每個參數組合從穩態快照跑1天即可（代表長時間又省算力）。
- **多 seed 只在最後收尾**（結論都定後跑最終 SC/EC 情境圖才用）；開發/調參全程單 seed。
- **最終 SC/EC「情境圖」**：建議用「穩態＋含區間調度」regime（最貼真實營運）、多 seed；單日版留對照。（情境 regime 待最後確認。）
