# 調度政策規則彙整（單一參考檔）

本檔集中記錄目前所有調度政策的完整規則與參數，方便對照/比較。
程式：`src/youbike_sim/dispatch.py`（`POLICIES` dict）；接入：`scenarios/real_system_scenario.py`。
設計脈絡與實驗結果見 `architecture_narrative.md`（§16–§23）。

> 分兩層：**區內（intra-district）**＝卡車在「行政區內各站點」間補/抽車（P1–P4，已實作）；
> **區間（inter-district）**＝母車在「行政區的集散場」之間搬車（規劃中，見最後一節）。

## A. 共用設定（所有區內政策皆同）

| 項目 | 規則 / 預設值 |
|---|---|
| 分區 | 真實 13 行政區，每區 ~145 站 |
| 集散場 | 每區一座，位於該區站點**幾何中位數**（Weber point）；緩衝庫存上限/初始 **300** 台 |
| 調度車 | 每區 N 台（預設 4，可掃 {2,4,6,8,10}）、容量 **30**、出車起始載 **15** |
| 健康帶 | LCL **20%**、UCL **80%**（站點車輛/容量比率） |
| 站點現況分型 | 到站掃描時：<LCL → 補到 **70%**；>UCL → 抽到 **30%**（避開靜態易多/易少在時段間翻轉） |
| 載量過濾 | 有車(load>0)才能補；有空位(load<30)才能抽（滿車只補、空車只抽） |
| 補/抽量 | 補 = min(車上現有, 目標補車量)；抽 = min(車上空位, 目標抽車量) |
| 行動量門檻 | 站點「**偏離目標 / 容量 ≥ `min_action_ratio`（預設 0.15）**」才值得服務。<br>**用比率非絕對台數**，避免小容量站被不公平過濾（小站每台車的比率變化更大）。<br>註：破 LCL/UCL 必使偏離/容量 ≥0.5，故此門檻 ≤0.5 等於「所有破門檻站皆值得去（含小站）」。 |
| 行駛時間 | 距離 ÷ 車速；車速 **N(50,10) km/h**、截斷下限 10 |
| 搬運時間 | 3 min + 0.5 min × 台數 |
| 資源耗盡 | 滿車無補站／空車無抽站 → 返集散場重置成 15 台 |
| 防呆 | stall guard：連續零延遲迭代 → 強制 timeout，避免無窮迴圈 |

### 設計理念與取捨（為什麼這樣設）
- **補到 70% / 抽到 30%（非 50% 中點）**：刻意「過度修正、留緩衝」。空掉的站(deficit)通常是高流出站（被借走）→ 補高到 70% 才撐得久；爆滿的站(surplus)通常是高流入站（被還爆）→ 抽低到 30% 才留得住空位。70/30 是「順著站點的下一步傾向」給緩衝，減少回頭再跑。對照組 UB 用 50% 中點（理想上界不在乎來回成本）。
- **score 距離常數 const（P1=0.1、dynamic/P7=0.5）**：① 防距離→0 除零；② 調「需求 vs 距離」的權衡——const 大(0.5) 淡化距離、優先衝最大缺口（大區尖峰該救火）；const 小(0.1) 重視就近、省里程。P1 走就近巡迴用 0.1；動態/P7 要追最痛點用 0.5。
- **健康帶 20/80**：對齊「優良時段占比」的定義窗（20–80%），讓「調度目標」與「評分標準」一致。
- **行動量門檻用比率(偏離/容量≥0.15) 而非絕對台數**：小容量站每台車的比率變化更大，用絕對值會把小站不公平地濾掉。
- **平方選站（dynamic/P3/P4）**：score 用偏離² 放大極端，讓「快空/快滿」的危急站優先於「只是偏一點」的站。
- **P7 用貪婪配對而非最優運輸**：先求簡單、且鏡像組員 Policy 2 便於對照；最優運輸（13×13 或站點層）幾乎一樣便宜，列為之後的精煉對照。
- **P7 保留集散場 fallback**：無盈餘可配時仍能動用集散場儲備補赤字、或把多餘停回集散場——維持守恆且不讓車卡在過滿站。

### 人力（與車綁定，套用 P2/P3/P4）
| 項目 | 規則 / 預設值 |
|---|---|
| 值勤窗 | 預設 06:00–24:00（可多段，`--duty-windows`）；窗外下班（不計薪、不出車） |
| 強制休息 | 連續工作 ≥ 240 min → 休息 45 min（不計薪） |
| 出車冷卻 | 每次返場後待命 10 min 才能再出車 |
| 工時計薪 | **值勤含待命**（休息不計薪）。P1/P4 例外：整班計薪（只在排定班次值勤） |

### 成本模型（DispatchingCost）
`Cost = C_labor·工時(hr) + C_km·里程(km) + C_trip·出車次數 (+ C_fix·車隊)`
預設（NT$，可調）：**C_labor=300/hr、C_km=8/km、C_trip=50/次**、C_fix=0（同車隊相消）。
- ServiceLevel = 1 − (缺車+滿站) / (借互動+還互動)。
- SC Ratio = ServiceLevel / DispatchingCost。
- 評估錨點＝真實 **true standard**（優良時段占比 0.607）；政策須達/超越才算不輸現實。

## B. 區內政策（已實作；`--dispatch-policy`）

### none（無調度 baseline）
不掛卡車。服務 floor。

### P1 `fixed`（固定巡迴）
- **觸發**：每日固定 **2 班**、各 **1.5 小時**（預設 06:00、16:00）。
- **選站**：候選＝破門檻且值得服務的站；`Score = |當前車數 − 目標| / (與卡車距離km + 0.1)`，取**最大**、**同分隨機**。
- **終止**：跑滿 1.5hr 時窗（做完窗內最後一單）；全區健康亦提早收工。
- **人力**：整班計薪（只值勤 2×1.5hr/車·日 → 便宜）。

### P2 `dynamic`（動態觸發，教科書原版）
- **觸發**：平時待命、每 5 分鐘（對齊網格）掃描；**有站 100% 滿/0% 空 或 ≥3 站破 80/20** 即出動（全車出動）。
- **選站**：`Score = (當前車數 − 目標)² / (距離km + 0.5)`，平方放大極端、取最大、**同分隨機**。
- **終止**：每完成一次補/抽即重掃，全區無「值得服務」站即返場待命。
- **人力**：全天值勤待命 → 貴。

### P3 `hybrid_anticipatory`（方案甲：排程預置 + 反應）
- **排程層**：尖峰前排定巡迴（同 P1 timing）做預先佈署（平方選站）。
- **反應層**：其餘時間在值勤窗待命掃描，**≥3 站破內警戒帶 10/90** 即反應式出車（平方選站）。
  （10/90 比 80/20 緊、比 0/100 早；避免 P2 在大區「幾乎全天觸發」的狂奔。）
- **終止**：反應出車後全區健康即返場；排程班跑滿時窗。
- **人力**：全天值勤待命 → 貴。

### P4 `hybrid_smartshift`（方案乙：排定班次 + 平方選站 + 提早收工）
- 同 P1 的固定 2 班 timing，但**班內用 P2 平方選站**、且**全區健康就提早收工**（不跑滿時窗，省成本）。
- **人力**：整班計薪（便宜）。

### P7 `pair_coord`（配對協調：全域 surplus→deficit 鏈式）
- **核心**：把區間 Policy 2「虛擬結算法／全域 flow 配對」套到**區內站點層**，攻多車協調損失（見 §35）。
- **觸發/人力**：待命族，全天值勤、每 5 分掃描由 `plan_move` 全域重解。
- **選任務**（`plan_move`）：① **pair**＝surplus(>UCL)→deficit(<LCL)，score = 可搬台數 /(車→盈餘+盈餘→赤字距離+const) 取最大；② 無配對有赤字且集散場有車 → 集散場→赤字；③ 只剩盈餘 → 盈餘→集散場。
- **執行**：鏈式「過滿站抽到 low target → 缺車站補到 high target」，`_claimed` 鎖配對兩端去重，**繞過集散場往返**。
- **vs P3 關鍵差異**：就近配對 + 直接 surplus→deficit 鏈式（省往返、優化協調），目標回收 P3 對 UB 的 ~0.05–0.10 協調損失。
- **可改良**：貪婪配對可換最優運輸（13×13 同樣便宜）；之後可加最優對照。

### 五方對照重點（24h weekday，見 §19、§21）
- 服務：P3≈P2（優良占比 ~0.50–0.58）> P4≈P1（~0.33–0.37，有 ~0.365 天花板）> none（0.26）。
- 成本：P1≈P4（便宜，只 2 班）≪ P2≈P3（貴，全天待命；人力佔 ~80%）。
- **無一達 true standard 0.607**（最佳 P3 n=10 = 0.584）。

## C. 區間政策（inter-district，規劃中）

### 背景：為何需要（重要發現）
區內調度下，**集散場幾乎全部耗乾**（P3 n=4：13 座有 10 座歸零；n=10：全歸零）。
集散場是綁定約束——白天 300 台 buffer 推完即空，下午無車可補 → 部分解釋服務卡在 true standard 之下。

### 組員設計：inter-district Policy 1「固定調度（無總部）」
- **對象**：母車在**各區集散場之間**搬車（非站點）。母車容量 **100**、車速 **30 km/h**。
- **觸發**：固定，一天 1 班，**凌晨 01:00** 出動（隔夜整備）。
- **集散場水位**：目標 300；LCL 150、UCL 450（Global Settings 提到「總部」補/抽，但本 Policy 1 為「無總部」＝只在集散場間直接搬，不用總部庫存）。
- **過程**：
  1. 掃描全部集散場，`Delta = Current − Target(300)`：盈餘區(Delta>0,可供)、赤字區(Delta<0,需補)、健康(=0,略)。
  2. 候選依母車載量過濾（滿→只補赤字、空→只抽盈餘、半載皆可）。
  3. 前往 `Score = |Delta| / (距離 + 0.1)` 最大者。
  4. 名單更新：供給/需求降為 0 即移除，回 step 1。
- **量**：補 = min(載量, 目標補量)；抽 = min(空位, 目標抽量)。handling = 3 + 0.5×台數。
- **終止**：供需都平衡（最佳）／單邊耗盡（多→就近卸回任一場後下班；少→無車可調下班）／05:00 強制收班。

### 我們的「最簡單 benchmark」與差異分析（討論中）
- **關鍵差異**：組員的「集散場間搬車」是**封閉式重分配**，只能修「集散場之間不平衡」。但我們實測集散場是**全部歸零（總量耗盡，非不平衡）** → 此政策在我們真實規模下會**近乎無效**（沒車可在場間搬）。它適用於組員「每區~20 站」理想化假設、集散場不會全空的情境。
- **我們真正的問題**＝總量耗盡：車卡在過滿的「站點」裡、集散場空。要解必須能把車從過滿站點/外部補回集散場，而非只在空集散場之間搬。
- **建議的最簡單 benchmark（隔夜整備上界）**：05:00 前把每座集散場**直接補回目標 300**（先不做路徑/時間），量測「整備到位」能帶來多少服務提升的**上界**；之後再用組員的母車路徑版逼近、看路徑成本。
  - 待定：補回的車來源——(a) 外部總部注入（破系統守恆，需計帳）或 (b) 隔夜從過滿站點抽回（守恆，較真實）。
- **控制變數**（你的要求）：區間跑夜間(01–05)、區內跑日間(06–24)，**時間上分離**，僅透過「集散場 05:00 庫存」互動。
  乾淨 A/B：{區內 P_x 單獨，集散場固定 300 起} vs {區內 P_x + 區間 benchmark}，其餘相同 → 隔離區間的純貢獻。

### 組員設計：inter-district Policy 2「虛擬結算法（Greedy Matching）」
與 Policy 1 不同——Policy 2 是**區級「轉移計畫求解器」**（先算 what，不模擬車）：
1. 盤點各區 `delta_bikes`（相對某目標的盈餘/赤字）→ 盈餘陣列、赤字陣列。
2. 建 13×13 距離成本矩陣（**區中心↔區中心**）。
3. **貪婪配對**：每輪挑距離最短一對，`Flow=min(盈餘剩, 赤字需)`，兩邊扣除、歸零移除，直到一邊清空。
4. 輸出任務清單（From/To/Flow/Cost(km)），可一對多（大盈餘區餵多赤字區）。

**定位**：卡在我們「瞬間整備上界」與 Policy 1「完整單車模擬」**中間**的*規劃層*。比 Policy 1 序貫單車眼光好。

**優勢**：規劃/執行分離乾淨；一對多靈活；任務清單可讀可報告；13×13 計算極快；天然接 §32「對快照驗證」（給目標分布算最小成本流）。

**缺失/劣勢**：
1. **貪婪≠最優**：最近對貪婪不保證解出運輸問題最優；但 13×13 最優（min-cost flow/運輸單純形）幾乎一樣便宜 → 用貪婪是不必要近似。建議兩者都跑、報告最優性差距（嚴謹度加分）。
2. **缺可行性/排程層**：母車容量 100、夜窗 01–05；計畫沒檢查多趟/多車是否裝得進時間+車隊預算。
3. **`delta_bikes` 目標未定義**（決定一切）：相對集散場目標 300 → 撞上「集散場早上全歸零」鐵證、近乎無效（同 Policy 1）；相對「區級站點+場 vs 區需求」且**容許抽過滿站點** → 才有實質意義。
4. 距離用區中心（我們集散場已在幾何中位數，差別小）；但盈餘要有具體來源。
5. **同 Policy 1 天花板**：只重分配既有車，解不了系統總量不足（UB-4 證瓶頸是吞吐，區間上限有限）。
6. 靜態一次性（當隔夜 benchmark 可接受）。

**預期結果**：定在集散場目標→白天幾乎無影響、SC 可能略降；定在區級總位置+抽過滿站→效益溫和（快照已是真實整備後、殘餘不平衡小）；成本便宜→若服務真有提升 SC 好看。**結論：優雅的規劃公式，但真實規模下白天服務槓桿偏小；最大價值＝乾淨 formulation + §32 對快照驗證工具。決定性槓桿仍是白天區內吞吐。**

**若採用，我們的改良**：(a) 用最優運輸取代貪婪（或兩者並陳）；(b) 加可行性/排程層（容量100、夜窗、母車數、真實 km/趟/工時）；(c) 盈餘/赤字定在區級總位置且容許抽過滿站點。

### 區間調度 target：`district_morning_peak_net_flow.csv`（組員提供，已檢查可用）
組員用早高峰平均淨流量推算的逐區 target（欄：sarea, net_flow_weekday, net_flow_weekend）。
**正數=補車（晨峰會流失的住宅origin區）、負數=抽車（晨峰會灌入的通勤dest區）。**
- 合理性 ✓：大安+562/文山+272/士林+263…（住宅,補車）；中正−169、臺大公館−271（機關/學校,抽車）。週末大幅縮小(無通勤)。符合通勤直覺。
- **關鍵：淨流量≠0**：weekday 補車需求 +2488、抽車供給 −440、**淨 +2048**；weekend +1119/−237/淨 +882。晨峰整體把系統抽乾(車騎去停公司沒還)。
- **→ 純區間重分配不夠（供440≪需2488）；缺口 +2048 由集散場儲備補**。解掉「集散場間重分配無效」的舊問題。
- **漂亮**：集散場儲備(4am 估 ~2589 wd) ≈ 晨峰淨缺口(2048)。系統儲備量剛好為晨峰預置而存在。
- 用法：當虛擬結算法的逐區 target；盈餘(負)→赤字(正)貪婪配對，不足由集散場儲備補。小提醒：'Unknown' 區(+5)忽略；區內分站由白天 P7 處理。

### 虛擬結算法 母車成本模型（定案 2026-06，使用者決策）
夜間母車成本**併入同一個 DispatchingCost 分母**（多日 SC = 總服務 /（白天調度＋夜間母車）），量綱與白天一致才可比可報告。
- **成本係數**（沿用白天那套）：C_km=NT$8/km、C_trip=NT$50/趟、母車規格 = 組員 Policy 1（容量 **100**、車速 **30 km/h**、裝卸時間 **3+0.5×台數** 分/訪，一趟取+卸兩訪）。
- **夜窗＝00:00→04:00＝240分**（使用者抓到）：白天 04:00 起跑，整備須 04:00 前完成（前一天 24:00=00:00 才能動）。**非 00:00–05:00**。
- **人力計薪（使用者選）＝按整班計薪（含待命，4hr）**：`labor = 母車數 × 4hr × C_labor_night`。`母車數 = ceil(夜間作業工時 / 240min窗)`。
  - **費率取夜班 NT$400/hr**（白天 300 ×1.33；改回 300 只動總成本 <0.5%，敏感度）。
  - **可行性（240分窗 OK但緊）**：每晚 6–8 母車、每車分攤 212–234min≤240（利用率~90–96%、緩衝小、建議多派1台/提早）；最長單趟 103–136min≪240。
- **路由＝兩段貪婪（虛擬結算法）**：
  1. **區間 surplus→deficit**（最近對貪婪，組員 Policy 2）：抽車區(cur>target)→最近補車區。
  2. **集散場儲備→赤字區**：剩餘淨缺口由中央儲備(≈城市形心)補。
  - 程式 `settlement_cost()` 每日按**實際 24:00→target delta** 精算（非寫死 CSV）。

## D. P6 預測式預置（hybrid_forecast，規格；P3 保留以利對照）

**核心**：利用 `λ_rent(站,小時)` 預測，**尖峰前提前佈署**，不等站點壞了才反應。預測+反應混合，但**P3 仍保留**（比較 P6 升級幅度）。

**四項已定（使用者）**：
1. **預測只用借走率 λ_rent（流出）**：predicted_outflow(站) = 未來 N 小時 λ_rent 加總。先**不估還入率**（流入）；之後有效再加（用於補車優先序）。
   - 限制：只看流出 → 會**預先補滿 source 站**（會被借空者），但**不會預先清空 sink 站**（會被還爆者，留給反應層處理）。
2. **固定預置時點**（概念單純）：在尖峰前的設定時點（如 05:30 晨峰前、15:30 晚峰前）各做一次預置，把站點一次佈署到「預測期末的理想位」。
3. **預測+反應混合**：預置時點做 forecast 預置；其餘時間用反應層（同 P3 的 ≥3 站破 10/90、band 30/70 選站）。
4. **預置目標水位** = `min(容量, 基準 + predicted_outflow)`。

**預置流程（pre-position pass）**：
- 對每站算 forecast_target = `min(cap, round(基準比率×cap) + predicted_outflow)`。
- 卡車貪婪服務「離 forecast_target 最遠」的站（載量可處理者）：低於→補、高於→抽，拉到 forecast_target。
- 受時間預算（如 90 分鐘）與載量/集散場限制。

**待你定的小參數**：
- (i) 預測horizon N（涵蓋尖峰）：建議 **3 小時**（晨峰 06–09、晚峰 17–20）。
- (ii) 基準比率：建議 **50%**（健康帶中點）作為「沒有預測流出時的水位」。
- (iii) 預置時點：建議 **05:30、15:30**（各尖峰前半小時）。

**實作要點**：需把 hourly λ_rent 傳入 dispatch（目前只有日總量）；新增 `_preposition_pass` 與 `hybrid_forecast_process`；POLICIES 加 `hybrid_forecast`，P3 不動。
